# 定投计划自动生成去重与补生成设计文档

## 1. 背景
当前系统已经支持：

- 在基金详情页创建定投计划
- 到达计划执行时间后，自动生成 `source = sip_plan` 的买入交易
- 将定投计划与交易记录一起保存到本地或云端
- 在计划超过结束日期时自动进入 `ended`
- 在计划为 `paused` 时停止自动生成

但现阶段的自动生成逻辑仍然偏“单步推进”：

1. 一次只处理当前 `nextExecutionAt`
2. 更依赖“计划状态刚好与交易状态同步前进”
3. 当用户多天未打开页面，或某次生成成功但计划推进未及时保存时，恢复能力不够稳
4. 当某一期该生成但因净值不可用而未生成时，后续补生成链路不够清晰

因此，本轮需要把定投计划自动生成能力从“能跑一次”升级为“可重复触发、可幂等恢复、可补最近漏期”。

## 2. 目标
本轮的目标是：

1. 防止同一计划在同一期次被重复生成交易
2. 支持用户在一段时间后再次打开页面时，补齐最近漏掉的应执行期次
3. 支持“交易已存在但计划推进状态未及时保存”的自恢复
4. 保持当前定投计划模型和云端结构基本不变
5. 将改动范围控制在自动生成逻辑与测试层，不扩大到 UI 重设计

## 3. 非目标
本轮暂不包含：

- 新增独立的定投执行日志表
- 回溯追补很久以前、已脱离当前 `nextExecutionAt` 推进链路的历史期次
- 引入真实交易日历或节假日顺延规则
- 新增用户可见的“补生成历史”界面
- 修改手工交易与自动交易的展示结构

## 4. 推荐方案
本轮采用“逐期回放 + 交易幂等去重”方案。

### 方案摘要
对于每个 `active` 且存在 `nextExecutionAt` 的计划：

- 不再只看当前这一期是否到时
- 而是从当前 `nextExecutionAt` 开始，逐期检查到 `now`
- 每一期都先判断是否已有对应自动交易
- 如果已存在，则只推进计划
- 如果不存在且能拿到净值，则补生成交易并推进计划
- 如果不存在且拿不到净值，则停止在当前期次，等待下次重试

## 5. 设计原则

### 5.1 幂等优先
同一个计划、同一个业务期次，无论逻辑被触发多少次，最终都只能落一笔自动交易。

### 5.2 缺失可恢复
如果之前某次已经生成了交易，但计划状态未同步推进；或者计划推进停在落后期次，系统应能在下次触发时自行恢复到正确状态。

### 5.3 保守补生成
只补从当前 `nextExecutionAt` 到 `now` 之间的最近漏期，不主动回补更久远的历史月份，避免旧数据状态不一致时产生大面积误补。

### 5.4 不跨越未知净值期次
如果当前应执行期次拿不到确认净值，则既不生成交易，也不继续推进后续期次，优先保证账本一致性。

## 6. 核心规则

### 6.1 处理范围
仅处理满足以下条件的计划：

- `status === active`
- `nextExecutionAt` 存在
- `nextExecutionAt <= now`

以下计划直接跳过：

- `paused`
- `ended`
- 没有 `nextExecutionAt`
- `nextExecutionAt > now`

### 6.2 期次推进方式
对于一个命中的计划，从当前 `nextExecutionAt` 开始，按 `frequency` 逐期推进：

- `daily`：+1 天
- `weekly`：+7 天
- `monthly`：+1 月

每处理完一个期次，再决定是否进入下一期。

### 6.3 去重键
自动生成交易的幂等识别键继续使用业务组合键：

- `source = sip_plan`
- `sourcePlanId = plan.id`
- `placedDate = 当前期次的下单日期`

即：

> 同一计划在同一下单日期，最多只能存在一笔自动生成买入记录。

### 6.4 每一期的处理分支

#### 情况 A：该期自动交易已存在
说明这期已经成功入账。

处理方式：
- 不再重复生成
- 将 `lastExecutedAt` 更新为当前期次 `executionAt`
- 继续推进到下一期

#### 情况 B：该期自动交易不存在，但能拿到确认净值
处理方式：
- 生成一笔新的 `buy` 交易
- 交易字段沿用当前自动生成口径：
  - `type = buy`
  - `amount = plan.amount`
  - `confirmedNav = resolveConfirmedNav(plan)`
  - `placedDate = 当前期次下单日`
  - `placedPeriod = plan.executionPeriod`
  - `effectiveDate = 根据 15 点前后规则推导`
  - `source = sip_plan`
  - `sourcePlanId = plan.id`
- 将 `lastExecutedAt` 更新为当前期次 `executionAt`
- 再推进到下一期

#### 情况 C：该期自动交易不存在，且拿不到确认净值
处理方式：
- 不生成交易
- 不更新 `lastExecutedAt`
- 不推进到下一期
- 保持当前 `nextExecutionAt`
- 等待下次重新尝试

## 7. 结束态规则
每处理完一个已完成期次后，都要计算新的下一次执行时间。

若新的 `nextExecutionAt` 超过：

- `endDate + 当天 23:59:59.999Z`

则：

- `status = ended`
- `nextExecutionAt = undefined`

否则：

- `status = active`
- `nextExecutionAt = 计算出的下一期时间`

本轮继续沿用当前项目已有的结束态判断规则，不额外改动结束日期语义。

## 8. 关键边界场景

### 8.1 重复进入页面 / 重复触发自动生成
即便同一计划在短时间内被多次 materialize，只要同一期次自动交易已存在，就不会重复生成。

### 8.2 交易已生成，但计划尚未推进
如果上次已经成功生成自动交易，但由于本地或云端保存过程未完成，计划仍停留在旧的 `nextExecutionAt`：

- 本次重跑时会先识别到该期交易已存在
- 因此只推进计划，不重复补单

这使得计划与交易状态具备自恢复能力。

### 8.3 某一期因净值缺失未生成
如果当前期次缺少确认净值：

- 当前期不生成
- 当前期不推进
- 后续期次也不提前穿透处理

这样可以避免跳过中间一期，导致账本期次断裂。

### 8.4 一次落后多期
如果用户在数周或数月后再次打开页面：

- 系统会从当前 `nextExecutionAt` 开始逐期尝试
- 对已存在的期次只推进
- 对缺失且可确认净值的期次补生成
- 直到处理到 `now` 为止，或在某个缺净值期次停下

### 8.5 同日存在手工买入
手工买入不参与本轮自动去重判断。

也就是说，即便同一日期已有用户手工买入，只要不存在同计划的自动买入记录，定投自动单仍可生成。

这样做更保守，也更符合当前数据语义：
手工买入不一定等同于该定投计划实际执行结果。

## 9. 实现影响面

### 9.1 主要改动文件
- `lib/funds/sip-plans.ts`
  - 将当前“单次检查”重构为“逐期回放”
  - 保留现有对 `effectiveDate`、`endDate` 的辅助规则

### 9.2 尽量不动的部分
- `lib/hooks/use-watchlist.ts`
  - 继续复用 `materializeSipPlans` 出参
- `lib/funds/types.ts`
  - 本轮不新增字段
- Supabase 表结构
  - 本轮不新增执行日志表

## 10. 测试建议
本轮至少补齐以下单测：

1. 已存在自动交易时，不会重复生成
2. 已到执行时间但缺交易时，会补生成
3. 连续落后多期时，会逐期补齐最近应执行期次
4. 某一期已存在、后一期间缺失时，能跳过已存在期并补后一期
5. 缺确认净值时，不生成、也不推进
6. 补生成到结束日期后，计划会正确进入 `ended`
7. `paused` / `ended` 计划不会参与自动生成

## 11. 成功标准
本轮完成后，应满足：

1. 同一计划同一期次不会重复生成自动交易
2. 用户数天后再次打开页面时，最近漏掉的应执行期次可以自动补齐
3. 即使交易已存在但计划推进状态落后，系统也能自动恢复
4. 缺确认净值时不会错误推进计划
5. 不需要新增新的数据库表或更改前端 UI 结构
